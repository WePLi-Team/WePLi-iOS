# 아키텍처 후보 — 추천하고 사용자가 고른다

플랫폼만 보고 정하지 않는다. `/project-setup`이 기획 · 기존 코드를 보고 **후보 2–3개를 비교해 하나를 추천**하고, 사용자가 고른 뒤에 `docs/conventions/architecture.md`를 쓴다. 고른 것과 이유는 `docs/decisions.md`에 DEC로 남긴다.

## 후보

| 후보 | 구조 | 잘 맞는 프로젝트 | 대가 | 프리셋 |
|---|---|---|---|---|
| **A. 가벼운 MVVM** | 기능 폴더 안에 View · ViewModel(또는 화면 훅) · Service. 규칙이 생기면 Service에 | 화면 10개 안팎, 비즈니스 규칙이 적음, 로컬 데이터 위주, 혼자 · 빠른 출시, 메뉴바 · 위젯 · 도구 앱 | 규칙이 늘면 ViewModel · Service가 비대해짐 → 나중에 B로 옮길 일이 생김 | `simple-mvvm.md` |
| **B. Feature-based Lightweight Clean** | View → ViewModel → UseCase → Repository, DI, Router, State Machine | 돈 · 권한 · 상태 전이 같은 규칙이 많음, 서버 + DB + 오프라인, 화면이 많음, 에이전트 병렬 개발 | 파일 수 · 초기 작업이 많음, 작은 기능에는 과함 | `clean-layered.md` + `clean-<플랫폼>.md` |
| **C. 지금 구조 유지** | 이미 있는 코드의 구조를 그대로 문서화 | 코드가 이미 꽤 있음, 구조가 일관됨 | 기존 구조의 약점도 같이 유지 | (기존 코드에서 작성) |
| **D. 단방향 상태 프레임워크** (TCA · Redux · MVI 라이브러리) | 상태 · 액션 · 리듀서 | 상태가 매우 복잡하고 그 도구에 익숙함 | 학습 · 의존성 · 보일러플레이트 부담. **사용자가 먼저 원할 때만** 후보로 | (사용자와 따로 정함) |

웹에서 화면 위주(콘텐츠 · 랜딩 · 관리 화면 몇 개)면 A의 변형으로 「프레임워크 기본 구조(Next App Router 등) 그대로」도 후보에 넣는다.

## 판단 기준 (기획 · 코드에서 확인해 근거로 쓴다)

| 기준 | A 쪽 | B 쪽 |
|---|---|---|
| 화면 · 기능 수 | 적다 | 많다 |
| 비즈니스 규칙 | 단순 표시 · 설정 | 계산 · 권한 · 정산 · 승인 흐름 |
| 상태 전이 | 거의 없음 | 주문 · 승인 · 구독처럼 단계가 있음 |
| 데이터 | 로컬 · API 한두 개 | 서버 + DB + 캐시 · 오프라인 |
| 테스트 요구 | 화면 확인 위주 | 규칙을 단위 테스트로 지켜야 함 |
| 개발 방식 | 혼자 · 순차 | 여러 에이전트 병렬 |
| 기존 코드 | 없음 · 작음 | 없음 (있으면 C를 먼저 검토) |

## 추천을 보여주는 방법

`AskUserQuestion`으로 후보 2–3개, 추천에 「(추천)」. 각 후보는 **사용자 입장에서 달라지는 것**으로 설명한다:
- 기능 하나 추가할 때 만드는 파일 수 (예: A 2–3개 · B 5–7개)
- 규칙이 바뀔 때 고치는 곳 (A: ViewModel · Service 여러 곳 · B: UseCase 한 곳)
- 테스트하기 쉬운 정도, 에이전트를 나눠 돌릴 수 있는지
- 나중에 바꾸는 비용 (A → B는 기능 단위로 점진 이전 가능)

추천 이유는 위 기준 중 이 프로젝트에서 확인한 것 2–3개로 쓴다(예: 「화면 8개 · 서버 없음 · 계산 규칙 없음 → A」).

## 고른 뒤 에이전트 구성

| 선택 | 쓰는 에이전트 | 지우거나 쉬게 둘 것 |
|---|---|---|
| A | `feature-agent`(기능 하나 전체: View · ViewModel · Service) · `reviewer` · `utility` | `domain-agent` · `data-agent` — 파일은 남기고 `agents.md`에 「사용 안 함」 |
| B | 전부 — 계약 먼저(domain) → feature ∥ data → 조립 | — |
| C · D | 기존 구조의 경계에 맞춰 A 또는 B 구성을 고른다 | — |

`verify_arch`도 고른 구조의 프리셋 것을 쓴다(A는 가벼운 검사, B는 계층 검사).
